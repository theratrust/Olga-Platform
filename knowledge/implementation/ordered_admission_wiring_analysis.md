# Ordered admission wiring readiness — DEV architecture analysis

Status: **analysis only**. No runtime, database, prompt, test, evaluator, or benchmark change. The offline prototype remains outside `bot.py`. This note evaluates wiring for the current single-poller private-chat DEV bot; it does not close send-after-/new or same-session completion ordering. Read together with `services/ordered_admission_prototype.py`, `services/ORDERED_ADMISSION_PROTOTYPE.md`, `knowledge/implementation/post_new_overtaking_analysis.md`, `knowledge/implementation/conversation_admission_race_analysis.md`, and `services/CONVERSATION_STATE.md`.

## Verified current path and exact aiogram seam

Read-only inspection of the installed DEV container found **aiogram 3.30.0**, source `/usr/local/lib/python3.11/site-packages/aiogram/dispatcher/dispatcher.py`. `requirements.txt` permits later versions (`aiogram>=3.0.0`), so these source assertions are version-specific.

| Location | Installed behavior | Relevance |
| --- | --- | --- |

| `Dispatcher._polling`, lines 354–411 | At 391–397 gets each update and constructs `_process_update`; default `handle_as_tasks=True` starts it in an independent `asyncio.Task` at 398–406. With `False`, line 411 awaits it. | **Exact pre-fan-out seam:** after the yielded `Update`, before lines 398–406. No public per-update callback is exposed at that point. |

With `handle_as_tasks=False`, middleware runs on the polling loop's awaited path. A raised DB error alone does **not** stop the poller from advancing. |

The prior prototype note correctly says **no middleware runs before default aiogram task fan-out**. A viable public-API alternative is to **turn default fan-out off**, then use a registered update-level outer middleware to commit short admission on the awaited path and explicitly start downstream work afterward. This does not require copying `_polling`. It is a composition of documented `start_polling(handle_as_tasks=False)` and `dp.update.outer_middleware`, but detached execution of the remaining handler chain needs application task supervision and offline proof. [aiogram 3.30 Dispatcher](https://docs.aiogram.dev/en/v3.30.0/dispatcher/dispatcher.html), [aiogram 3.30 middleware](https://docs.aiogram.dev/en/v3.30.0/dispatcher/middlewares.html).

**Recommended integration:** a small `services/ordered_ingress.py` update middleware registered after the built-in FSM middleware; set `handle_as_tasks=False` in `bot.py`. For each update, classify the narrow private-coaching cases, await its atomic admission/reset (and the short required FSM transition), create an immutable result, then schedule the remaining aiogram handler chain as a supervised task with that result in copied middleware data. Return from middleware so the poller advances. Do not await model generation, transcription, evaluator work, Telegram sends, or unrelated slow handlers on the polling path. For irrelevant updates, dispatch the normal handler chain promptly as a supervised task too; otherwise `handle_as_tasks=False` would serialize all admin, quiz, and other work. The task supervisor must collect exceptions and drain/cancel on shutdown; aiogram's own task set no longer tracks these application tasks. Returning early also changes aiogram's per-update completion/handled logging and any returned `TelegramMethod` handling; inspect/test those semantics before wiring. Existing handlers generally send via awaited methods, but the integration must not assume every route does.

Subclassing/overriding `Dispatcher._polling` could insert directly at the exact seam, but it overrides a **private** method and repeats its polling/backoff/semaphore/task lifecycle logic (roughly 50–100 lines now, more if `_listen_updates` is copied). A custom loop around public `Bot.get_updates` and `Dispatcher.feed_update` avoids private inheritance but must own offset, retry/backoff, signal shutdown, allowed-update resolution, and task lifecycle; it is larger than this DEV slice. There is no supported callback around `_listen_updates` or `_polling` that by itself commits phase 1 before their default task fan-out. Prefer the public-API composition first; pin/test aiogram 3.30 before deployment because even public middleware-chain behavior can change.

## Narrow ingress classification and handoff

Only incoming `Update.message` objects with private `chat.id == from_user.id` and positive original `message_id` are candidates. Classify `/new`, ordinary coaching text, and non-admin voice/audio; all other message/update types pass through without creating/rotating coaching state. Admin voice is a separate control route and must not be intercepted as coaching. Non-private coaching remains ignored as today. Classify against the same route contract as `handlers/chat.py`: `/new` uses aiogram `Command("new")`, while ordinary text uses `F.text & ~F.text.startswith("/")`; voice uses `F.voice | F.audio`. A naive `text == "/new"` parser is insufficient for mention/caption/argument cases. The installed `Command` filter can await `bot.me()` for mentions, so ingress must use a cached bot identity or a route-parity-verified parser rather than making an unexpected network call inside phase 1. No full handler, model call, or content-based ordering is needed.

The ingress should check FSM eligibility before normal coaching admission and perform /new's short FSM `AI_CHAT`/shadow-ID update in the ordered phase. The DB remains the conversation source of truth. `handlers/chat.py:82–93` currently rechecks FSM and calls `admit_user_message`; `cmd_new` at 45–62 currently rotates. In a wired path those operations must run **exactly once** at ingress, and downstream must require the captured result. Normal text has its content already: keep the existing atomic `admit_user_message` insert for text, extended only as needed for duplicate safety. /new continues to use the existing atomic `rotate_conversation` transaction, then its downstream sends the current acknowledgement. The existing 20-row history, ledger scoping, assistant/draft conditional writes, and method prompt remain unchanged.

Recommend a frozen result (status `admitted|rejected|reset`, source update kind, `(chat_id,message_id)`, captured `conversation_id`, reason category, and a persisted/reservation reference when needed) passed under a dedicated key such as `ordered_admission` in a **copied aiogram middleware `data` mapping**. Aiogram's handler call prepares keyword arguments from that mapping; downstream coaching handlers should take the result explicitly and fail closed if it is missing/mismatched. The voice handler calls `ai_chat_handler` directly today, so it must explicitly pass the same result to a shared downstream function; ordinary aiogram dependency injection does not occur on that direct Python call. Downstream must not look up the current conversation ID as a substitute and must not call user admission/rotation again. It may check that the captured ID is still active before later writes, as current code already does.

| Handoff carrier | Assessment |
| --- | --- |
| Attach to `Update` or `Message` | Reject. Installed aiogram models report `frozen=True`; an offline assignment to `Message.text` raised Pydantic `ValidationError`. Current `handlers/voice.py:85` assigns `message.text = transcribed_text`; future wiring should pass transcript as a separate value rather than relying on this mutation. |
| `contextvars` | Task context is copied at task creation, but authority becomes ambient and hard to audit in direct handler calls. Avoid for session identity. |
| FSM/data | The **middleware data dictionary** is the recommended transport for an immutable result. FSM storage itself is only UI/observer state and must not become the persistence authority. Copy data for the detached task. |
| Side map by update/message ID | Requires cleanup, can be lost on restart, and risks key collision or misassociation. Avoid as authority. |
| Custom wrapper object | Could be explicit but aiogram's router expects its `Update`/`Message` types; adds translation work. Avoid for this slice. |

## Voice contract and DB primitives

The prototype's voice port is simulated. Real `handlers/voice.py:31–38` downloads and transcribes **before** `ai_chat_handler` performs admission. Phase 1 must instead bind the original voice/audio marker to the current DB conversation before network transcription, without inserting fabricated text into `chat_messages`.

| Option | Crash/duplicate/history behavior | Assessment |
| --- | --- | --- |
| A. Durable marker reservation, later conditional transcript commit | A small admission record captures user/chat/message/conversation and status. No history row until transcript succeeds. Duplicate marker can be recognized atomically. A crash may leave a reservation requiring expiry/recovery; it does not invent text. | **Preferred.** |
| B. Placeholder `chat_messages` row, later update | Placeholder can appear in latest 20 and ledger source, may survive failed transcription, and changes history semantics. | Reject. |
| C. Process-local reservation only | Minimal schema but lost on crash/restart, no durable duplicate fence, and a confirmed update may never be replayed. | Insufficient for a reliable voice path. |
| D. Delay all voice admission until transcript | Keeps current DB primitive but reopens the 103-before-102 race for voice. | Reject. |

Conceptually add a small `inbound_admissions` table (or equivalent minimal keyed record) with a unique key on **`(user_id, chat_id, message_id)`**, `conversation_id`, kind, and reservation/commit/failure status. No transcript, raw audio, or psychological state belongs there. For text, create the admission record and `chat_messages` row in the **same SQLite transaction** as current cutoff/session checking; a duplicate must not add another user row or launch another generation. For voice, `reserve_inbound_admission(..., kind=voice)` atomically checks cutoff/current ID and writes only the record. After transcription, `commit_user_content(reservation, transcript)` atomically checks the same reservation, status, user, and **still-active captured conversation ID**, inserts the transcript once into `chat_messages`, and marks committed. A stale reservation after /new must fail; no remapping to B. Failed/empty transcription marks failed or expires without a history row. /new should invalidate/delete old pending reservations in its existing transaction, while preserving only minimal duplicate/audit metadata for the chosen retention period. An idempotent re-delivery returns a deterministic already-admitted/duplicate result and must not produce a second acknowledgement, transcript row, draft, or model run. Existing legacy rows lack markers and should not be adopted. This is an **additive DEV migration proposal only**, not an implemented schema change.

A split primitive for **all** inbound messages gives one uniqueness rule and a shared voice/text contract, but text should retain its single atomic insert path; do not force text through two separately committed steps. A voice-only reservation table plus new marker columns on chat history would require two duplicate mechanisms. The shared keyed admission record is the smallest coherent durable option identified. It does **not** by itself guarantee generation after a crash; recovery would also need an inbox/replay policy and enough source metadata to retry without storing raw audio.

## Acknowledgement and UI transitions

| Path | Current timing | Recommended wired timing |
| --- | --- | --- |
| Text | After atomic user insert, typing action, history/ledger assembly, and prompt construction; before `generate_candidate` (`handlers/chat.py:94–135`). | After ordered text insert succeeds; retain copy and position relative to generation as practical. No positive acknowledgement for rejected/duplicate/stale turns. |
| Voice | Typing action before transcription; on failure an error reply; on success it delegates to text handler, which acknowledges after its later admission (`handlers/voice.py:31–86`). | Marker reservation before transcription; positive coaching acknowledgement only after transcript is conditionally committed to the captured active ID. A transcription failure produces no fake history row or positive coaching acknowledgement; retain existing failure copy. |
| /new | DB rotation and FSM update under local lock, then current “Начинаем новый разговор…” reply (`handlers/chat.py:45–62`). | Ordered reset commit and short FSM transition first; same reply downstream, only for accepted reset. |

The proposed ingress only sequences **message admission**. Callback queries are not incoming Message events with comparable `message_id`; the referenced bot message ID is not the callback's arrival marker. `open_ai_chat` changes FSM to `AI_CHAT` after a Telegram send; quiz callbacks update state and some sleep for seconds. They **must be coordinated with /new at the FSM transition boundary**, but should not enter message-ID comparison or hold ingress during rendering/sends. `/start` is a Message with its own marker and calls `state.clear()`; its short FSM transition should be ordered with /new and text eligibility even though it does not rotate the DB conversation. Purely informational callback rendering can remain outside admission sequencing. In the first runtime slice, if these transitions remain delegated as today, claim only the restricted text/voice/new 101/102/103 property when no competing UI transition occurs; do not claim complete FSM consistency. Admin/moderation routes stay available and keep the existing stale-draft checks.

## Polling confirmation, restart, and process ownership

`bot.py:198–203` calls `init_db()`, `bot.delete_webhook(drop_pending_updates=True)`, then `dp.start_polling(bot)` with default 10-second polling timeout and default task fan-out. In aiogram 3.30 `_listen_updates`, local `GetUpdates.offset` advances **after** the generator yields and the consumer requests the next item; Telegram considers an update confirmed only when a later `getUpdates` request carries an offset above its `update_id`. [Telegram Bot API](https://core.telegram.org/bots/api#getupdates). With current default task fan-out, offset progression does not wait for handler completion. With the recommended awaited middleware phase, it waits for **phase-1 return**, not downstream completion. A DB exception is caught by `Dispatcher._process_update` and returns a handled flag; simply raising from middleware would still let polling advance. A bounded retry/fail-stop or durable inbox is required before relying on Telegram redelivery for DB failures. Startup's `drop_pending_updates=True` independently prevents guaranteed replay after restart.

| Crash point | Persisted state | Redelivery / loss classification |
| --- | --- | --- |
| A. Before admission commit | No user turn/reset committed. | May be redelivered if Telegram has not received a confirming higher offset and pending updates are retained; current startup drops pending updates, so loss is possible. |
| B. After admission but before handler fan-out | Text row or /new cutoff is durable; voice reservation would be durable. | Downstream work may be lost. Duplicate replay must be idempotent. |
| C. After user persistence but before generation | Row remains in the captured conversation unless a later /new intentionally clears it. | The user may have no generated answer. Session isolation survives, response delivery does not. |
| D. During generation | Existing stale assistant/draft write guards still protect a later /new. | Generation/ack/send can be incomplete or user-visible; same-session completion order and send-after-/new are separate risks. |

Telegram guarantees getUpdates offset confirmation and limited retention; the aiogram offset/fan-out placement above is **installed 3.30 implementation**; the current startup drop choice is **application code**. No local queue or DB cutoff can reconstruct an unseen update once it is discarded.

Read-only DEV inspection found one bot service in `docker-compose.yml`, `restart: always`, and one `python bot.py` process in the DEV bot container (`docker compose ps/top bot`). The repository search found no second DEV polling launcher. A second external process, systemd/cron entry, replica, or reuse of the same secret token **cannot be disproved from repository/config inspection without inspecting other deployments or secrets**, which was not done. The operational invariant for this design is **exactly one polling owner for this bot token**. If violated, two independent middleware streams can each process later messages before the other's /new; the local ordering proof fails even though the DB cutoff still rejects known stale markers. Deployments must enforce and monitor this invariant before production.

## Architecture decision record

**Decision.** Plan an awaited `dp.update.outer_middleware` with `start_polling(handle_as_tasks=False)`, short atomic admission/reset, immutable DI handoff, and application-supervised concurrent downstream tasks. No runtime wiring is authorized by this analysis.

**Exact aiogram integration seam.** `Dispatcher._polling` after `_listen_updates` yields intact `Update`, before default task creation at lines 398–406. The public composition suppresses that task creation and executes the middleware in the awaited `_process_update` path; it is not a direct pre-task callback.

**Why.** It sequences phase 1 in the one polling stream without holding generation behind /new and without copying aiogram internals. The existing DB cutoff remains the durable cross-session fence.

**Text path.** Classify private eligible text, atomically insert content and unique marker under the captured DB ID, then pass the immutable admitted result to downstream. No second admission.

**Voice path.** Atomically reserve marker/ID without transcript, transcribe later, commit transcript only if reservation and captured ID remain active, then use normal coaching downstream. Empty/failed/stale transcripts never create placeholder history rows.

**/new path.** Ordered existing DB rotation/cutoff/delete and short FSM transition, then unchanged acknowledgement downstream. A stale duplicate reset gets no positive acknowledgement.

**Downstream handoff.** Copied aiogram middleware data carries a frozen result; handlers require it explicitly. No object mutation, ambient context, or side map.

**Restart semantics.** DB commit survives; downstream may not. Current startup drops pending updates and aiogram catches DB exceptions before the poller sees them, so replay and error-stop guarantees require separate work.

**Single-poller invariant.** Exactly one polling owner per bot token; observed one DEV Compose bot process, no proof about token reuse elsewhere.

**Private-api risk.** Recommended path uses public APIs but relies on verified 3.30 middleware/polling composition; pin and contract-test. Do not override private `_polling` unless the public approach fails.

**Alternatives rejected.** Default handler-level lock (scheduler order), full-handler `handle_as_tasks=False` (blocks generation), private dispatcher fork (upgrade churn), placeholder voice history (junk/inference), process-only voice reservation (crash/duplicate loss), and mutable Message/Update state.

**Risks.** DB failure can still advance aiogram's offset; confirmed updates and startup drop can be lost; voice needs a durable primitive; callback/start FSM transitions can race; detached task supervision and semantic parity need tests. Send-after-/new and same-session response ordering remain separate production blockers.

**Rollback strategy.** Remove the new middleware/flag/DI wiring and return to the documented current DEV behavior while retaining existing DB session/cutoff/ledger safeguards. Any additive admission-table migration should be backward compatible and inert when wiring is disabled.

**First runtime wiring slice.** Conceptually, pin aiogram 3.30, add an offline contract test for `handle_as_tasks=False` plus update middleware, then wire **only** private text, voice-marker reservation, and /new to a small ordered ingress service. Use a keyed disposable-DB migration and mandatory immutable handoff; detach long work with a supervised task registry. Keep callback/start transition ordering and restart-delivery guarantees explicitly gated for a later slice rather than claiming production readiness.
