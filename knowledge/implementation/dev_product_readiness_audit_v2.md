# Olga Coaching DEV product readiness audit, v2

Date: 12 October 2026. Branch: `feature/method-core`. Scope: offline inspection of the current code and tests, including the recent durable resume, quiz, callback, voice, and `/start` changes. This report supersedes the **findings**, not the file, of `dev_product_readiness_audit.md`; that earlier document and the historical sections of `returning_user_resume_design.md` describe older baselines. The six-scenario multi-turn finding remains: single-turn quality is good, multi-turn coherence is weak. Coaching style is outside this product audit. `DEV_DIRECT_CHAT` is configurable and defaults to false in `bot.py`; the running DEV configuration was not inspected. No live product, model, transcription, Telegram, or database operation was used.

## Decision

**C. ONE BLOCKER REMAINS BEFORE USER TESTING.** The principal start-to-return journey is now coherent in offline tests, but `/new` still admits a **new or otherwise ineligible private user into volatile `AI_CHAT` without a completed quiz or durable coaching eligibility**. `handlers/chat.py:cmd_new` rotates/creates an active session and sets `AI_CHAT` without checking `users.coaching_eligible`; `ensure_coaching_state` trusts an already-`AI_CHAT` FSM. A subsequent text (or voice) in that same process enters the ordinary generator path. This bypass is distinct from the known `/new` ordering race and from safe fresh-FSM recovery: after a restart, the unmarked user is again denied. The current test `test_new_does_not_grant_unmarked_user_resume` proves only that latter denial and explicitly observes the earlier `AI_CHAT` state. No `/new` button is on the current first-run UI, but the command remains directly callable. An onboarding requirement that can be bypassed by a normal bot command is a product integrity blocker, even for controlled DEV testing.

**Recommended next step: 3. FIX ONE OTHER SPECIFIC BLOCKER FIRST** — require existing durable coaching eligibility before `/new` can set `AI_CHAT` or rotate a conversation for a non-eligible user, with a clear non-destructive route back to onboarding. This is a later, narrow admission/UX slice; no implementation is made here. It need not reopen the documented concurrent-update race. After that gate, begin controlled DEV user testing with the limitations below stated to testers. Do not wait for durable mid-quiz progress or another coaching prompt experiment.

## End-to-end journey and previous-blocker comparison

A first-time private user sends `/start`, sees the existing welcome photo and quiz button, then receives Q1–Q3 sequentially. A valid answer mutates score/answers once and advances the stored expected message ID. At `CALC`, the result button validates every recorded answer and score sum; mapping remains **0 → Свет, 1–3 → Полутень, 4–6 → Тень**. It writes `users.test_result` and `quiz_result_verified=1` before displaying result/entry UI. A current, completed `open_ai_chat` button writes `coaching_eligible=1`, ensures the active conversation, sets `AI_CHAT`, and invites a user message. The verified result is optional coaching context, not an eligibility substitute or a diagnosis. A completed-result user who has not clicked coaching entry remains ineligible; after FSM loss `/start` offers onboarding again, which is a limited UX edge, not a false promotion.

Text coaching verifies the original private message marker, uses the per-user admission lock and atomic DB admission under the active ID/cutoff, builds the prompt with the verified result or no archetype, reads the latest 20 session rows plus a bounded deterministic carry-forward ledger from current-session history, and acknowledges before generation. The generator's provider-declared length guard triggers one retry with the same payload. A successful direct response is sent then conditionally persisted; moderated mode stores a PENDING draft for admin approval/edit/reject. This path remains subject to the known late `/new` delivery/order limitations. No coaching-style judgment is inferred from these wiring checks.

Voice and audio share the private/eligibility preflight before Telegram file work, then use the original update marker and the same chat pipeline after transcription. A returning eligible user after fresh MemoryStorage gets the same active ID/cutoff and verified context for text and voice. `/start` gives that user a read-only home; Continue restores the current conversation without calling the model. `/new` for an **eligible** user retains durable eligibility/result while rotating the active ID, setting cutoff, deleting old chat history/PENDING drafts, and leaving no old rows for recovery. The ineligible `/new` route is the blocker described above.

## Failure and moderation paths

- **Generation:** Explicit `length` is rejected before delivery or draft creation; one retry succeeds or the generic communication-error reply is sent. A second length or other failure leaves the admitted user row but no accepted assistant/draft. The 350 cap is unchanged. A provider `stop`/missing finish reason with nonempty but semantically incomplete text is outside this deterministic guard; historical three harness outputs cannot be retrospectively classified without metadata. Empty output has no dedicated gate. The fixed waiting acknowledgement may precede a later generic error or a silently suppressed stale response.
- **Voice:** `get_file`, `download_file`, byte reading, and chat-action failures can escape the handler; transcription exceptions are swallowed by `services/transcription.py` into empty text, producing the visible recognition error. A valid transcript is not previewed but enters the existing text path. Direct/moderated downstream handling is the same as text. Voice/audio are supported; other codecs and format validation were not added.
- **Moderation:** With `DEV_DIRECT_CHAT=false`, the user receives the waiting acknowledgement while a PENDING draft is stored and sent to admins with approve/edit/reject controls. Approval/edit checks active draft/session, sends to user, then saves assistant history/status; reject changes admin/draft state but sends no user update. `/new` removes PENDING drafts. Returning text and voice use the same draft route and verified quiz context. Tests prove draft scoping and stale rejection, but no live moderation account or configured-mode observation was used.
- **DB and state errors:** Atomic admission/rotation/result transactions roll back on failure. Admission, quiz result persistence, and pre-generation history/quiz-context reads may raise outside the chat generator's user-facing catch. A failed ledger read alone logs a warning and falls back to recent history. This is limited failure UX, not evidence of routine failures.

## Interrupted quiz assessment

A normal quiz takes three questions and its progress is volatile. A process restart during those few minutes loses partial answers; old callbacks show the inactive-button alert rather than corrupting the score. The user can send `/start` and repeat from Q1. That costs at most the partial attempt, not coaching history or a completed verified result. A text message sent before `/start` has no guidance and can be mistaken for a broken bot. Likelihood is bounded by the short quiz duration and DEV restarts but is nonzero during active development. Persisting every answer/step plus callback authority would be a medium persistence and migration slice with its own replay semantics; that cost is not justified as a prerequisite to a small, instructed DEV cohort. **Rating: LIMITED BUT ACCEPTABLE FOR DEV**, provided testers know to use `/start` after an interrupted quiz. This does not solve the `/new` bypass.

## Copy and supportability

Concrete copy issues only: the new-user welcome asserts a particular partner/relocation motive before the user's input; `👉 Задать вопрос` understates that a statement can begin coaching; the result/learn-more prose may overstate what a three-question score establishes. The returning copy (“С возвращением. Ты можешь продолжить текущий разговор.”), Continue confirmation, inactive-button alert, and generic provider communication-error reply are short and usable. `/new` correctly says prior chat history is cleared, while its retained verified quiz result is not explained. These are LIMITED UX issues, not reasons to reopen the coaching prompt.

Privacy-safe diagnostics can identify **successful** state restoration (mode and conversation ID), rejected quiz/home callbacks by category, explicit truncation retry, generic provider error kind, and stale admission/write operations. They cannot readily tie a reported silent return, vanished quiz, missing archetype, or no-answer acknowledgement to one end-to-end user turn without inspecting sensitive state; home missing-session is logged under the quiz-callback label. `generate_candidate` supports an opt-in sanitized observer, but chat does not pass one. Transcription logs an exception string, so its privacy safety cannot be guaranteed solely from code. **Supportability: LIMITED** for controlled testing, with tester-provided time/command/context useful; no logging change is made here.

## Remaining priorities and test gate

**Top two remaining product risks only:**

1. **BLOCKING — `/new` bypasses onboarding in the current process.** It is a direct route from an ineligible private account to generation, despite the durable eligibility contract. Fix this narrow admission gap before inviting target users.
2. **LIMITED — interrupted quiz can look silent after FSM loss.** Old buttons fail safely; `/start` restarts Q1, but a plain text return gives no direction. Accept for a controlled cohort with explicit restart guidance; do not enlarge this audit into quiz-progress persistence.

**Three areas now good enough:** (1) durable text and voice resume with current ID/cutoff and optional verified context; (2) quiz scoring/persistence and sequential callback integrity; (3) contextual `/start` home plus explicit eligible-user Continue. Keep the multi-turn harness as a regression benchmark and avoid renewed prompt tuning during this product gate.

Validation for this audit: `pytest -q tests` passed **1,087 tests**. `git diff --check` is reported separately in the final task report. No live user journey was run, so this verdict is an offline readiness decision, not an observed Telegram launch result.
