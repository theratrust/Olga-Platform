# Архитектурный анализ: компактное состояние разговора в Olga Coaching DEV

## Область, источники и статус

Это анализ исходников ветки `feature/method-core` в `/opt/olga-coaching-dev`, без реализации и без проверки запущенного бота. Под «состоянием» ниже понимаются данные для сборки запроса, а не психологическое состояние клиента. Наблюдения об эффективности любой новой схемы остаются гипотезой до отдельного сравнения. Фактическое значение переменных окружения и содержимое БД не проверялись.

Канонические источники сверки: [метод_Ольги.md](../method/метод_Ольги.md), [принципы.md](../method/принципы.md), [границы.md](../method/границы.md), [паттерны.md](../method/паттерны.md), [язык_и_стиль.md](../method/язык_и_стиль.md), [карта_коучингового_разговора.md](../method/карта_коучингового_разговора.md), [примеры_коучинговых_разговоров.md](../method/примеры_коучинговых_разговоров.md), [поведение_AI_бота.md](../method/поведение_AI_бота.md). Также учтён [AI_поведение_gap_analysis.md](AI_поведение_gap_analysis.md). Строки кода ниже относятся к состоянию checkout при чтении; это не утверждение о PROD.

Статус требований различен. Прямо подтверждённые в файлах метода положения: не давать готовое решение и автоматические варианты; помогать человеку прийти к собственному ответу ([метод_Ольги.md](../method/метод_Ольги.md), строки 11–29; [принципы.md](../method/принципы.md), 3–23). Авторство, запрет приписывания, диагноза и давления, свобода отвергнуть гипотезу — действующие границы/рабочие правила этих материалов, но не все являются отдельно подтверждёнными прямыми цитатами Ольги ([границы.md](../method/границы.md), 3–39; [принципы.md](../method/принципы.md), 27–61). Учёт отвеченного, снижение повторов, форма ledger и порядок его обновления — **производные архитектурные решения**, а не новый метод ([карта_коучингового_разговора.md](../method/карта_коучингового_разговора.md), 30–45, 175–205; [поведение_AI_бота.md](../method/поведение_AI_бота.md), 17–23, 62–81, 325–341). Синтетические примеры показывают возможные ходы, не единственный правильный ответ ([примеры_коучинговых_разговоров.md](../method/примеры_коучинговых_разговоров.md), 682–695).

## 1. Текущий путь информации к генератору

1. В Telegram текстовый чат работает только в FSM `AI_CHAT`; некомандный текст обрабатывает `handlers/chat.py:49–59,224–227`. У обычного пользователя голосовая транскрипция заменяет `message.text` и проходит тот же handler; административный voice идёт отдельным запросом с другим prompt и без истории чата (`handlers/voice.py:20–82`).
2. Handler сначала сохраняет текущий user-текст в `chat_messages`, затем получает FSM-данные: `archetype` (fallback «Полутень») и `shadow_conversation_id` (`handlers/chat.py:70–89`). `first_name` приходит из Telegram-профиля. Эти имя и тестовый результат добавляются в системную инструкцию. ID нужен только для shadow observers; в prompt и SQL-фильтр он не входит (`handlers/chat.py:80–93,192–203`).
3. `build_coaching_prompt` формирует системную инструкцию из базового prompt, имени, результата теста и пяти файлов ядра (`prompts/coaching.py:4–140`; `services/methods/loader.py:9–15,41–64`). Карта, примеры и поведение_AI_бота не загружаются в генерацию. Текущий prompt уже запрещает скрытые мотивы, готовые варианты, диагнозы, архетип как доказательство и заполнение «я не знаю» (`prompts/coaching.py:15–65`).
4. `get_recent_history(user_id, limit=20)` читает роли и тексты из БД. `build_messages` добавляет единственное `system` сообщение перед упорядоченной историей. Текущий user-текст уже внутри истории, отдельно не добавляется (`handlers/chat.py:91–93`; `services/coaching_generator.py:13–15`). `generate_candidate` передаёт это `messages` в один явный chat completion с `max_tokens=350`, который ограничивает вывод, а не входную историю (`services/coaching_generator.py:18–33`).
5. В direct chat отправленный ответ затем сохраняется как `assistant`; при модерации сначала сохраняется только pending draft, а в историю попадает лишь одобренный/отредактированный отправленный ответ (`handlers/chat.py:112–135`; `handlers/admin.py:142–150,242–250`). Отклонённый/неотправленный черновик не следует считать услышанным пользователем. Acknowledgement и сообщение об ошибке тоже не записываются как assistant через chat history (`handlers/chat.py:95–101,214–222`). Реальный режим direct chat определяется `DEV_DIRECT_CHAT`; его значение здесь не читалось (`bot.py:39–42,159–175`).
6. `bot.py:55` использует `MemoryStorage` для FSM. `/new` удаляет `chat_messages` по `user_id`, переводит FSM в `AI_CHAT` и меняет shadow ID (`handlers/chat.py:33–47`; `database.py:186–195`). `/start` очищает FSM, но не историю БД (`handlers/start.py:13–22`). `open_ai_chat` меняет FSM-стадию без очистки БД (`handlers/callbacks.py:67–80`). В прочитанном коде нет TTL/автоматического истечения разговора. После перезапуска FSM в памяти исчезает; БД остаётся. Поэтому перезапуск не равен `/new`.
7. Существующая «сессия» не является надёжной DB-границей: `chat_messages` не имеет `conversation_id` (`database.py:35–44`), чтение и удаление фильтруют только `user_id` (`database.py:164–195`). Позднее одобрение старого draft после `/new` может записать старый ответ в новую историю; конкурентные сообщения также требуют отдельной проверки. Это риск из структуры кода, не заявленный наблюдавшийся инцидент.

**Итог на момент generation:** одна системная инструкция с методом/именем/результатом теста и максимум 20 последних сохранённых user/assistant сообщений. FSM-метаданные за пределами имени/архетипа не образуют память диалога. Выявленной conversation-state summary или ledger в запросе нет.

## 2. Точная граница усечения и порядок ролей

Точка Telegram-усечения — `handlers/chat.py:91`, где передаётся `limit=20`. Реальное усечение исполняет SQL `ORDER BY id DESC LIMIT ?` в `database.py:164–175`; `reversed(rows)` в строках 177–183 возвращает выбранные сообщения в возрастающем порядке ID. Это **совместно handler-limit и DB-query-limit, по числу сообщений**. Дефолт DB-функции равен 10, но этот путь явно задаёт 20. Генератор только приклеивает system и не обрезает историю; токенового/символьного лимита на вход или отдельного генераторного усечения в прочитанном пути нет. Лимит 350 относится к выводу. Полная история остаётся в БД до `/new`, но не передаётся модели.

В обычном чередовании на запросе 11-го user-сообщения есть 21-я запись (11 user, 10 assistant): самая ранняя user-реплика уже выпадает, окно начинается с assistant. Учитываются **записи, а не пары ходов**; при модерации возможны несколько user подряд или запоздалый assistant, так что выпадение может наступить в другой момент. Сначала теряются самые старые формулировки темы, прямые ограничения/цели, уже отвеченные вопросы, отвергнутые гипотезы и поправки. Порядок оставшихся ролей не нарушается, но может исчезнуть вопрос или гипотеза, к которой относится видимый ответ/отказ. Старый вывод assistant нельзя реконструировать как факт клиента.

Отдельно: benchmark не читает БД и не использует Telegram/FSM (`services/conversation_benchmark.py:1,148–165,177–186`). Он добавляет user в локальный список, берёт `history[-20:]`, зовёт тот же `build_messages`/`generate_candidate`, затем добавляет успешный assistant; при неуспехе сценарий прекращается (`services/conversation_benchmark.py:183–205`). Таким образом, запросный размер и порядок в нормальном чередовании похожи, **источник истории, reset, модерация и persistence различаются**. Нынешний corpus ограничен 5–8 user-ходами на сценарий (`services/conversation_benchmark.py:44–52`), поэтому потерю после 20 записей не проверяет. `tests/run_dev_generator_diagnostic.py:30–47` тоже собирает локальную историю и передаёт `history[-20:]`; это ещё один отдельный harness.

## 3. Какие сведения нужны и как не смешивать их статусы

| Категория | Пример | Допустимое представление | Ошибка |
| --- | --- | --- | --- |
| A. Явные слова пользователя | «Я не хочу возвращаться к этой теме» | Короткая точная цитата/фрагмент с user message ID; актуальная область действия «сейчас/пока», если названа | Усилить до «никогда не хочет говорить» |
| B. Отвеченный разговорный пункт | Assistant спросил о значении работы; user: «Работа мне важна, но график нет» | Пара `question_ref` + дословный user-фрагмент **только при однозначной связи**; иначе A без метки «отвечено» | Объявить любой следующий user-текст ответом на предыдущий вопрос |
| C. Отвергнутая гипотеза assistant | Assistant предположил страх зависимости; user явно: «Нет, это не про страх зависимости» | Ссылка на реально предъявленную гипотезу + дословный отказ; rejected остаётся статусом гипотезы, не диагнозом | Сохранить «страх зависимости» как характеристику клиента |
| D. Производное служебное состояние | «Вопрос уже получил явный ответ»; «эту гипотезу не возобновлять без инициативы user» | Метка поверх доказанных B/C, с источниками и возможностью отмены; инструкция по обращению с событием | Объявить тему навсегда закрытой или предписать следующий ход |
| E. Психологическая интерпретация | «Она боится зависимости», «конфликт идентичности» | Не создавать как состояние. Даже если user сама употребила эти слова, хранить только её высказывание A с её модальностью, не объективную оценку E | Скрытая интерпретация становится памятью и затем «доказательством» |

Полезны устойчивые **явные ограничения, поправки и отказы**, а также проверенные пары вопрос–ответ: они снижают вероятность повторить именно известный вопрос/гипотезу. «Незавершённая тема» допустима лишь как прямо оставленный user вопрос/желание продолжить, с её словами и временным статусом; не как диагноз, стадия карты или обязанность вернуться. Не хранить самоназначенный коучем фокус. Если клиент повторно поднимает тему, текущая инициатива открывает её независимо от прежней метки. «Я не знаю» сохраняет отсутствие ответа; это не `answered`, не скрытый мотив и не основание предложить варианты ([принципы.md](../method/принципы.md), 37–39,57–61; [карта_коучингового_разговора.md](../method/карта_коучингового_разговора.md), 143–173).

**Жёсткая техническая граница:** произвольную русскую речь нельзя надёжно классифицировать детерминированно как ответ, отказ от конкретной гипотезы или «открытую тему». Совпадение «нет» с предыдущим вопросом само по себе недостаточно. В первом срезе лучше пропустить неоднозначное событие, чем маркировать его уверенно. Если будущая задача потребует широкого семантического покрытия, это отдельный проект извлечения с проверкой ошибок, а не скрытое обещание детерминированного ledger.

## 4. Варианты размещения и формы

| Размещение | Плюсы | Цена/риск | Вывод |
| --- | --- | --- | --- |
| Только FSM/session | Нет миграции; простой `/new` | `MemoryStorage` теряется при рестарте, тогда как DB-история остаётся; `/start` очищает FSM без очистки истории; нельзя доказать согласованность с DB | Не делать единственным источником |
| Отдельно хранить state в БД | Выживает после рестарта; можно обновлять по ID | Новая таблица/миграция, атомарность с `chat_messages`, очистка `/new`, поздние drafts, rollback и чувствительные дубликаты | Отложить до доказанной потребности |
| Формировать каждый ход из текущей DB-истории | Нет нового хранилища/миграции; `/new` очищает источник; воспроизводимо | Дополнительное чтение всей текущей истории, строгая фильтрация, верхняя граница размера выводимого ledger; гонка с конкурентной записью | Предпочтение для первого среза |
| Hybrid: recent raw + extractive ledger | Сохраняет локальные нюансы последних 20 и несколько старых явных событий | Потребует адаптации сборки контекста и benchmark; неправильная метка всё равно опасна | **Рекомендуемая форма** |

**Рекомендация:** короткая недавняя сырая история как сейчас + маленький **детерминированный extractive ledger**, вычисляемый на каждом ходе из DB-истории текущего разговора. Это hybrid по контексту, но без LLM summary и без нового persisted state. Источник уже хранится в `chat_messages`; производный ledger не записывается в БД или FSM. Отдельный локальный read должен получать полный разговор в порядке ID (при росте — пагинация/потоковая обработка), а в модель отправлять только ограниченные, не дублирующие последние 20, подтверждённые события. Нужны лимиты числа записей/символов и приоритет явных границ/поправок; нельзя превращать ограничение вывода ledger в неограниченный token spend. При недоступности источника или неоднозначной связи — пустой ledger и текущий baseline request; не выдумывать восполнение.

Форма: **структурированные события + короткие цитаты пользователя и ссылки на сообщения**; не свободный пересказ. Полный event log в prompt шумен, а свободный summary может сжать «я пока не хочу работать» в «боится работы». Структура нужна для проверки происхождения и отмены. Бесконечная копия всех фактов также не нужна: хранить только те короткие, явно высказанные фрагменты, которые реально рискуют выпасть и влияют на повтор/границу.

### Сравнение четырёх кандидатных дизайнов

1. **Только удлинить raw history сверх 20.** Самый простой эксперимент, без экстрактора. Повышает шанс присутствия раннего ответа, но не гарантирует, что модель им воспользуется; порядок и семантический статус гипотез остаются задачей модели. Входные токены/стоимость/latency растут вместе с длиной и могут быть непредсказуемы без input budget. Старые, уже отменённые реплики и неподтверждённые гипотезы становятся шумом. Не выбирать как основной фикс; отдельный небольшой controlled arm полезен для сравнения.
2. **Детерминированный ledger.** Прозрачные источники, лёгкое удаление/исправление, ноль дополнительных модельных вызовов. Безопасен только при узких правилах допуска; общий semantic answer detection детерминированно не решён. Выбрать как компактный компонент, не обещая полноту.
3. **LLM free-text summary.** Может охватывать больше диалога, но добавляет вызов/стоимость/ошибки, дрейф при повторном сжатии, диагнозоподобные выводы и риск превращения summary в авторитетнее текущих слов. Отдельный summarizer, тот же generator или evaluator-like model несут одну и ту же проблему происхождения; evaluator не должен становиться источником фактов. Не выбирать.
4. **Hybrid.** Последние 20 raw сообщений + узкий ledger из старых явных событий. Локальная связность остаётся, старые ограничения доступны компактно. Опциональную extractive summary **не включать в первый срез**: пока нет доказательства, что простого ledger недостаточно. Если позже понадобится, она должна копировать только source-linked user-фрагменты, не интерпретировать.

### Минимальная логическая схема (не миграция)

```text
conversation_state = {
  explicit_user_statements: [{source_user_id, quote, scope}],
  answered_items: [{question_assistant_id, answer_user_id, answer_quote}],
  rejected_hypotheses: [{hypothesis_assistant_id, rejection_user_id, rejection_quote}]
}
```

Здесь `source_user_id` означает ID **сообщения** в `chat_messages`, не Telegram user ID; имя лучше уточнить при реализации. Все ID — локальные ссылки для проверки/отмены, не часть текста модели. `scope` берётся из явной формулировки («пока», «сейчас», «эту тему») или остаётся неопределённым; нельзя добавлять вечное действие. Отдельные `active_user_topics`, `unresolved_user_questions`, `explicit_user_goals`, `user_preferences_or_boundaries` и `explicit_user_wording_to_preserve` как постоянные поля в первом срезе избыточны: явные актуальные границы/цели/вопросы можно представить в `explicit_user_statements` с цитатой; «активность» и «неразрешённость» требуют интерпретации. Не хранить `topic_already_explored` как факт.

| Поле | Допуск и источник | Не допускать; update/conflict | Reset, хранение, видимость |
| --- | --- | --- | --- |
| `explicit_user_statements` | Краткая дословная фраза из сохранённой user-роли с явным желанием, границей, целью, поправкой или собственным вопросом; source ID обязателен | Не извлекать мотив, диагноз, содержание из assistant/test; добавлять только при строгом распознавании, не нормализовать «пока» в «никогда». Более поздняя явная поправка снимает/заменяет старую запись; при сомнении удалить | Пересборка из DB на ход; `/new` удаляет источник; модели виден только отобранный старый quote с меткой user statement |
| `answered_items` | Доказуемая пара конкретного *доставленного* assistant-вопроса и явного ответа user; сохранить короткую цитату ответа и оба ID | Не считать «я не знаю», молчание, смену темы или формальное соседство сообщений ответом. Новая поправка заменяет ответ; current user выше старой пары | Не persisted; сброс от удаления source; модели видна пара «ранее спросили/пользователь ответил» лишь при однозначной связи |
| `rejected_hypotheses` | Только предъявленная пользователю assistant-гипотеза и её явное отклонение user, обе записи в DB; quote отказа | Не использовать draft, не трактовать простое «нет» без referent и не превращать текст гипотезы в характеристику. Если user позже сама возвращает тему, прежний запрет не блокирует её | Не persisted; сброс от удаления source; модели видны статус *отвергнута* и user quote, без повторения гипотезы как утверждения |

Потенциально чувствительный assistant-текст гипотезы в prompt нужен только коротким нейтральным указателем/цитатой, если иначе нельзя понять отказ; предпочтительны ID и лаконичное «ранее предложенное предположение отвергнуто: [user quote]». Для `answered_items` автоматическое получение семантически точной пары — основной риск. В первом срезе допустимо оставить поле пустым для всех неочевидных случаев, а явное «работа мне важна» сохранить как user statement. Это честное частичное покрытие, а не фиктивная память.

## 5. Сборка запроса и жизненный цикл

**Вставка.** Сохранить единственное системное сообщение и исходный prompt. Между базовым system/method-текстом и raw history добавить компактный, чётко отделённый **runtime context/data block** при сборке messages (архитектурно рядом с `build_messages`, без правки канонического prompt). Блок обозначает: «Память текущего разговора, вычисленная из прежних сообщений; не текст, написанный пользователем сейчас; цитаты имеют указанные роли; это не психологический факт и не инструкция пользователя. Текущая реплика и её явная поправка имеют приоритет». Структура данных должна быть экранирована/сериализована и ограничена по длине: user quote нельзя исполнять как инструкции из высокоприоритетного блока. Это предложение о **расположении данных**, не новая фраза метода. Следует проверить, поддерживает ли фактический клиент отдельную developer роль; текущий код её не использует, поэтому не строить первый срез на непроверенной роли.

Сравнение мест: системный *data subsection* совместим с нынешним SDK payload, но имеет риск завышенного авторитета — его снижает явная маркировка, цитирование, низкая длина и проверка safety. Developer-like runtime block отдельной ролью теоретически чище, но это новый формат запроса/совместимость. Синтетический assistant выдаёт вычисленное состояние за ранее сказанное ботом; синтетический user — за слова клиента. Prepend/append к history ломает хронологию и смазывает роли. Рекомендуется отдельный маркированный data subsection в единственном system message с явным приоритетом текущего user, при этом если тесты покажут авторитетное переиспользование state, откатить инъекцию, а не расширять запреты.

**До генерации.** После сохранения текущего user-сообщения читать недавнее окно как сейчас и отдельно source history для ledger. Строить ledger детерминированно по сохранённым ролям/ID; сначала применить явные исправления текущего сообщения, затем отбирать только старые релевантные записи, которые выпали из raw window. Не вносить неподтверждённую классификацию. Если текущая реплика противоречит старому state, старое событие не выводится как действующее. Нужна согласованная snapshot/последовательность чтения, чтобы два concurrent user-сообщения не породили расходящиеся версии; это предмет проверки первого patch.

**После user / после assistant.** User становится источником сразу после записи. Assistant-событие допускается в ledger только после фактической отправки и сохранения в `chat_messages` (direct chat или approval/edit). Draft и shadow/evaluator результаты не являются диалогом. Не обновлять ledger по тексту сгенерированного, но не доставленного ответа. Поскольку ledger вычисляется заново, отдельного mutation после ответа нет.

**Поправка / отказ.** Более поздняя ясная поправка user имеет приоритет; старая запись убирается или маркируется отменённой при пересборке. Отказ от гипотезы связывается с конкретной ранее доставленной гипотезой, если связь доказуема; не переспрашивать и не защищать её. Если связь неоднозначна, сохранить только явные слова пользователя как границу, не назначая «отвергнутую гипотезу». Новая текущая просьба клиента обсудить прежнюю тему имеет приоритет над старым `do not reopen`.

**`/new` и expiry.** При рекомендованном неперсистентном ledger `/new` удаляет DB-источник, значит следующая пересборка пуста; новый FSM shadow ID не используется как DB boundary. В первом срезе нет отдельного state для удаления. Нужно проверить запоздалое одобрение старого draft и параллельный `/new`; иначе старый assistant может вновь появиться в DB. У текущего runtime нет явного session-expiry/TTL: не придумывать таймер. Если позже появится expiry, он должен чистить/разграничивать и raw history, и ledger одновременно; истечение только FSM было бы несогласованным. После рестарта raw DB сохраняется и ledger можно восстановить, но пользователь должен вновь войти в `AI_CHAT` из-за `MemoryStorage`; `/start` сейчас не стирает DB-историю.

**Persistence/rollback.** Выводимый ledger не хранить ни в FSM, ни отдельной таблице. Новых колонок, миграции и DB rollback для первого среза нет; потребуются read-only методы чтения полного текущего разговора, а не модификация схемы. При отключении feature flag/удалении сборки ledger запрос снова равен baseline. Для альтернативы DB-persisted state потребовалась бы таблица с `user_id`, conversation epoch, source message IDs, типом/quote, revision и каскадом очистки; миграция и согласованное удаление при `/new`, плюс rollback без влияния на `chat_messages`. Эта сложность пока не оправдана. Старые записи истории уже хранятся в БД; рекомендация не расширяет срок хранения.

## 6. Что никогда не помещать в память и риски

Не хранить диагнозы, типы личности, архетип как доказательство, предполагаемые эмоции/мотивы, «истинную причину», readiness/stage/resistance, гипотезу assistant как факт, evaluator labels/scores, rejected/pending drafts, технические ошибки, имя/username как разговорный факт, полный голосовой файл, необязательные длинные цитаты и дубли всех raw сообщений. Не превращать слова партнёра в факт о его намерении. Работа/проект не становятся целью из «хочется своего» ([поведение_AI_бота.md](../method/поведение_AI_бота.md), 194–222). Не хранить запрет вернуться к теме дольше явно указанного пользователем срока.

1. **Семантическая ложная метка.** Правило может неверно распознать ответ или адресат «нет»; ложный `answered/rejected` хуже пропуска. Строгий допуск, source IDs и fail-closed.
2. **Авторитет state в system.** Даже дословная цитата может получить статус «истины» или инструкции. Явная маркировка роли, подчинение текущей реплике, отсутствие интерпретаций и контроль benchmark.
3. **Устаревание/поправки.** «Пока» и изменившееся мнение нельзя фиксировать навсегда; поздняя поправка должна отменять старое событие, при неопределённости выводить меньше.
4. **Граница сессии/гонки.** `/new` удаляет по user ID, draft может прийти позже; FSM restart и `/start` не эквивалентны новому DB-разговору. Нужны адресные тесты и, если риск подтвердится, отдельное решение по epoch/изоляции.
5. **Приватность и объём.** Дополнительное локальное чтение всей истории, цитаты в запросе и возможные логи увеличивают поверхность раскрытия чувствительного текста. Минимизировать поля/длину/время жизни, не логировать raw ledger, не отправлять его evaluators автоматически, не включать личные данные в benchmark artifacts. При отказе чтения не пытаться угадывать память.

## 7. Проверка до PROD

**Unit/offline без сети/DB-записи:** на синтетических role/ID последовательностях проверить извлечение, source links, отсутствие assistant draft, порядок, лимиты и экранирование; current user override; исправление прежней информации/смену мнения; «я не знаю» не становится ответом; явный отказ от гипотезы не становится психологическим фактом; партнёр «не запрещает» не превращается в контроль; «хочется своего» не превращается в работу. Проверить `/new` как пустой источник, restart/re-entry и поздний approval отдельно. Уточнить, какие фразы экстрактор сознательно пропускает. Golden payload test должен сравнить точные роли и позиции system/data/recent/current user.

**Benchmark:** существующий `services/conversation_benchmark.py` создаёт 5–8 ходов и локальный `history[-20:]`; для длинных сценариев (>20 сообщений) потребуется отдельный будущий тестовый harness или изменение валидатора в отдельной реализации — данный анализ его не меняет. Синтетические сценарии: (1) ранний явный ответ о работе; (2) ранний отказ от гипотезы; (3) явная поправка и смена решения; (4) повторное «я не знаю»; (5) старая тема вне raw окна; (6) `/new`; (7) current message вновь открывает тему; (8) слова партнёра и восприятие клиентки; (9) работа/автономия без автоматического трудоустройства; (10) >20 сообщений с модерацией/нечередующимися ролями. Проверять не только presence ledger, но и случаи, когда событие намеренно отсутствует.

Сравнить frozen baseline, longer-raw-only arm и hybrid при одинаковых синтетических входах/настройках модели. Сначала offline payload/инварианты; любые live model calls — только в отдельном будущем эксперименте. Использовать нынешние methodology/quality показатели и ручной обзор релевантности, повторов, progression, естественности, отказов/поправок и reliability/latency/token cost; **новых evaluator dimensions не требуется**. Ранние Candidate A/B и узкий history-aware guard дали отдельные улучшения при более широких регрессиях; это основание для консервативного парного сравнения, не доказательство пользы ledger ([AI_поведение_gap_analysis.md](AI_поведение_gap_analysis.md), 188–206). Нельзя считать улучшение non-repetition компенсацией нарушений авторства или приписывания.

## ADR

**Decision.** Для будущего минимального DEV-эксперимента: сохранить 20 последних raw сообщений и добавлять небольшой, вычисляемый детерминированно из сохранённого текущего разговора extractive ledger явных user-высказываний и только доказанных пар ответа/отказа. **LLM summary не использовать. Производное state отдельно не сохранять.**

**Why.** Сохраняет ранние слова/поправки при минимальной дополнительной сложности, без второго модельного вызова, новой БД-схемы и приписывания внутреннего состояния. Точность важнее покрытия; user и его текущая реплика остаются первичны.

**Alternatives rejected.** Удлинение raw history не гарантирует учёта и повышает шум/стоимость; FSM-only теряет согласованность после restart; DB state добавляет миграцию и гонки; LLM free-text summary допускает дрейф и скрытую интерпретацию; полный event log перегружает context.

**Risks.** Ложное извлечение, авторитетность блока, устаревшая граница, `/new`/late draft race, чувствительный текст и стоимость полного DB-чтения. Все проверять до любого PROD-решения.

**Rollback strategy.** Убрать/выключить сборку ledger: исходные DB-сообщения и baseline system + последние 20 вновь формируют запрос; миграций и данных нового типа для отката нет.

**First implementation slice (только концепция).** Отдельный read-only builder получает DB-сообщения текущего разговора с ID, выбирает несколько коротких явных user-границ/поправок вне recent window по строгому allowlist, проверяет source/role/актуальность, добавляет маркированный data block к запросу; несколько offline тестов проверяют `/new`, конфликт с текущим сообщением и отсутствие выдуманных мотивов. Поля ответов и отказов активировать лишь там, где есть проверяемая однозначная связь; расширять покрытие только после измерения false positives. Это описание, не изменение runtime.
