# Post-/new overtaking and valid-turn loss — DEV architecture analysis

Status: analysis only. This document describes current behavior and a proposed direction; no runtime, schema, prompt, test, evaluator, or benchmark behavior changes here. Scope is the single-poller private-chat DEV bot at commit b752fab. The send-after-/new and same-session completion-order races remain separate.

## Evidence and current path

- `bot.py` constructs `Dispatcher(storage=MemoryStorage())`, calls `init_db()`, then `delete_webhook(drop_pending_updates=True)` and `dp.start_polling(bot)` with defaults. The DEV Compose file defines one bot service; that is a deployment configuration, not a distributed ordering guarantee. `requirements.txt` says `aiogram>=3.0.0`, so the installed-version findings must be rechecked after dependency upgrades.
- Read-only inspection inside the running DEV bot container found aiogram **3.30.0**. Its `start_polling` defaults to `handle_as_tasks=True`; `_polling` iterates updates and starts `asyncio.create_task(_process_update(...))` without awaiting each handler. `_listen_updates` yields each item in a `getUpdates` response before setting the next offset. The app supplies no `events_isolation`, so `Dispatcher.__init__` installs `DisabledEventIsolation`. These are installed-library implementation observations, not a Telegram promise that handlers start or finish in update order.
- `handlers/chat.py` has separate `cmd_new` and `ai_chat_handler` tasks. Both take the same short `admission_lock(user_id)`. `cmd_new` calls `rotate_conversation` and updates FSM under it. Normal text checks FSM and calls `admit_user_message` under it, then releases it before history, acknowledgement, generation, observer work, draft creation, and delivery. Lock acquisition order is scheduler order.
- `database.py` uses `BEGIN IMMEDIATE` for both operations. `rotate_conversation` compares the previous cutoff, stores a new conversation ID and cutoff, and deletes that user's chat rows and pending drafts in one transaction. `admit_user_message` compares the incoming positive private-chat marker with the **cutoff already present** and inserts a user row tagged with the then-current conversation ID. This protects a delayed 101 after cutoff 102, and rejects an older /new 102 after /new 104. It cannot know about a /new update that has not executed.
- `handlers/chat.py` sends a typing action and later a “Спасибо за твой вопрос…” acknowledgement **after** successful DB admission but **before** generation. That commit can still be undone by a later-running /new with an earlier Telegram message ID. In moderated mode the same admission precedes draft generation. `handlers/voice.py` downloads and transcribes before delegating the original Telegram Message to `ai_chat_handler`, widening the scheduling interval.
- Latest-20 history and ledger reads require user ID plus conversation ID. Assistant and draft writes require the captured active ID. Those guards cannot recover a valid turn already deleted from A by /new. `tests/test_conversation_admission.py` has a deterministic overtaking case documenting that outcome.

## Exact failure and what can be known

For one private chat, Telegram message order is 101 (normal), 102 (/new), 103 (normal). Active conversation is A. Aiogram may schedule 103 first. It passes the local lock, finds no 102 cutoff, inserts its user row in A, releases the lock, and may send the acknowledgement. Later the 102 handler acquires the lock, rotates to B with cutoff 102, and deletes A's rows and pending drafts. The 103 turn is now absent from B history and from the ledger; its A-tagged response/draft later fails the active-ID write check. The user may have seen an acknowledgement without a retained turn or answer. This is **persisted-turn loss and user-visible loss**, not cross-session contamination. It blocks production readiness.

At 103's DB transaction, the durable row has exactly the same relevant state in two worlds: (a) no /new 102 exists, and (b) /new 102 exists but its task has not run. A cutoff check, current-conversation lookup, or high watermark cannot distinguish them. A local lock can serialize whichever task arrives first but cannot discover an unseen 102. Message ID 103 alone does not reveal whether 102 was /new, a non-coaching message, an outgoing bot message, or absent. No correctness claim can rest on a short sleep.

Once the 102 cutoff is committed, the current design correctly rejects 101 and admits 103. The remaining problem is **ordering before that commit**. It can be addressed without serializing generation only by moving ordered admission to an ingress phase that runs before concurrent long work, subject to the input stream's ordering contract.

| Ordinary private/basic-group message IDs increase in Telegram's underlying update model. | **Documented Telegram lower-level behavior; applicability is a contract assumption for this Bot API private-chat slice** | [Telegram update sequences](https://core.telegram.org/api/updates). The current DB cutoff already makes this ordinary-private-message assumption. Bot/outgoing or otherwise unhandled messages can create gaps, so `103 - 101 = 2` cannot prove that 102 was delivered to this bot. |
| The currently installed aiogram poller iterates returned updates, but creates a separate task for each by default. | **OBSERVED IMPLEMENTATION, aiogram 3.30.0** | Read-only `Dispatcher._listen_updates`, `_polling`, and `start_polling` inspection inside DEV bot container; `bot.py` passes no override. Iteration order does not imply handler admission order. |
| Enabling `SimpleEventIsolation` would lock by FSM `StorageKey` (default strategy `USER_IN_CHAT`) across the entire handler invocation. | **OBSERVED IMPLEMENTATION, aiogram 3.30.0** | `FSMContextMiddleware.__call__` holds `events_isolation.lock(context.key)` while awaiting the handler; `SimpleEventIsolation` uses an `asyncio.Lock` per key. It does not sort by message ID. Here it would also serialize long model generation for that user. |
| Two updates for one private chat necessarily *begin handlers* or *acquire locks* in message-ID order. | **NOT GUARANTEED** | aiogram task fan-out and awaits allow overtaking. |
| Bot API explicitly promises that every private-chat message-ID ordering relation is reflected in the order of all update types delivered to this poller, including callbacks. | **NOT ESTABLISHED by the cited API text** | The design must verify the relevant delivered-stream contract, and must not silently treat callbacks as messages or fill unseen gaps. |

The Bot API offers update IDs to restore update order if delivered out of order, but a receiver cannot order an update it has not yet received. The current single polling connection and aiogram iteration give an ordered *observed* sequence; the proof for 101/102/103 is conditional on 102 being observed before 103 at ingress. A second poller/webhook worker or changed delivery configuration invalidates that local proof.

## Options compared

| Option | Can it prevent the stated 103-before-102-handler race? | Cost and limit |
| --- | --- | --- |
| 1. aiogram FSM event isolation / per-user full-handler serialization | **No guarantee of message order.** It may serialize 103 first. | `SimpleEventIsolation` holds through the full handler, including OpenRouter and Telegram awaits; different users have different keys, but one user's generation blocks /new. Its locks are process-local. Do not enable it as this fix. |
| 2. Explicit per-user ordered admission queue | **Yes for updates already enqueued in verified ingress order**, if /new and normal messages share it and admission is drained before generation. | Needs lifecycle, backpressure, duplicate handling, restart behavior, and a rule for unseen earlier updates. A queue fed by independently scheduled handlers can still receive 103 first; sorting available items cannot identify an unseen 102. An in-memory queue alone is not a crash-safe correctness fence. |
| 3. DB high watermark / expected-order fence | **No, alone.** The row cannot know 102 is pending before 102 runs. | A high watermark can reject duplicates and regressions after observation, but cannot infer `next_id`; message IDs have gaps from unobserved/outgoing events. Keep the existing durable /new cutoff as the useful DB fence. |
| 4. Short grace/reorder window | **No deterministic guarantee.** | May reduce common scheduler overtaking but adds latency and fails whenever 102 is delayed beyond the window. It cannot justify acknowledging 103. Do not make it the correctness mechanism. |
| 5. Sequence admission at polling ingress before handler task fan-out | **Yes for the single ordered polling stream when 102 is observed before 103.** | Requires separating short admission/reset/state transition from long handler work. It must not advance/confirm beyond an uncommitted ingress item. Existing aiogram `handle_as_tasks=False` serializes entire handlers and is therefore not the intended implementation. |
| 6. Hybrid: ordered ingress + short per-user admission + DB cutoff | **Preferred**, with the explicit single-stream ordering premise. | The ingress order decides when phase 1 executes; the existing DB cutoff protects late/stale tasks and survives restarts. Long work runs concurrently after phase 1. More complex than a single lock but smaller than a generic durable messaging platform. |

A watermark or buffer can be diagnostic, but neither turns an unseen future /new into known state. If updates can arrive at ingress out of Telegram logical order without a complete upstream order signal, **no finite in-process wait or current DB field can guarantee both no loss of 103 and no premature admission**. That is an information limit, not an implementation bug.

## Preferred architecture: ordered ingress, short admission, concurrent work

Use one polling owner for the bot token and introduce a narrow **ordered ingress stage before aiogram's per-update task fan-out**. For each private-chat coaching message update, complete phase 1 in the order of the observed polling stream, using message ID as a same-chat consistency check and the existing DB cutoff as the durable stale fence. A single ingress consumer can keep different users independent by submitting short per-user admission operations in stream order and awaiting each user's phase-1 completion before submitting the next event for that user; it need not await phase 2 or block other users. A simple global short phase-1 sequencer may be an acceptable first DEV implementation if it does not include network/model work; per-user lanes are preferable for resilience to one user's DB fault.

**Phase 1 — ordered admission:** validate private chat and positive original message marker; classify normal message or /new; apply the current FSM eligibility transition as required; atomically insert the user turn under the captured conversation ID, or atomically rotate/delete and store /new cutoff; capture result. For text, the user text is available immediately. For voice, classify and reserve/capture its logical conversation *before* download/transcription; later text insertion must be conditional on the captured ID and must not fabricate a history row or a synthetic marker before transcription. This voice reservation is a conceptual requirement, not present in current code. Do not let the current voice download run ahead of /new ordering. A later /new may legitimately invalidate unfinished work from an earlier message.

**Phase 2 — asynchronous work:** history/ledger load, voice transcription, generation, evaluation/observer work, draft creation, and Telegram delivery run outside the ordered ingress section. Keep existing conditional active-ID writes and scoped history. Two generations in one conversation may still complete out of order; this analysis does not solve that race. An old response can still be sent after /new; this analysis does not solve that race.

The existing short per-user lock can remain to coordinate local FSM and DB operations if the ingress design needs it. Its acquisition is **not** the ordering source. No ordering lock should span an OpenRouter, evaluator, audio download/transcription, or Telegram send await. DB is still the source of truth for the active conversation.

**Acknowledgement:** send a positive “working on it” acknowledgement only after phase 1 has committed for that message and its placement cannot be undone by an *earlier* /new that has not yet passed the ordered ingress point. Send it before generation if desired. Never acknowledge a stale/rejected/unknown-order turn as accepted. Current acknowledgement is post-DB-commit but can precede a logically earlier reset; the proposed ordering closes exactly that gap under the stream-order premise. Acknowledgement and Telegram delivery are not transactional with SQLite; the separate send race remains.

## Callbacks, quiz, and non-message updates

`/new`, text, and voice are Message updates with original positive private-chat message IDs. Voice needs early classification and conversation capture because transcription currently precedes the shared chat handler. Callback queries (quiz and `open_ai_chat`) have their own `update_id` and reference a possibly old **bot message**; that message's ID is not the callback's Telegram send-order marker. `handlers/callbacks.py` and `handlers/quiz.py` can mutate FSM, and some quiz handlers sleep or make Telegram calls. They must not be held as whole handlers in the short ingress critical section.

For the first slice, route callback/quiz **eligibility and short FSM transitions** through the same observed update-stream ordering boundary, or bind a callback to the conversation ID captured when it was offered and reject it if stale. Do not compare a callback's referenced message ID directly with the /new cutoff. Leave long quiz rendering/sends outside. Any callback that can re-enter AI_CHAT after /new must be checked against the then-current DB ID; FSM cannot authorize a stale conversation. If that split is deferred, callback/FSM overtaking remains a separate production risk and should be named explicitly. Admin/moderation control paths should retain their existing routing and stale-draft checks.

## Crash, restart, failure, and multiple processes

An in-memory per-user queue is safe only as a coordination aid. Telegram retains updates for at most 24 hours; `getUpdates` confirms updates when a later offset is requested. Aiogram's default poller may advance to the next offset while a spawned handler is still uncommitted. Also `bot.py` currently calls `delete_webhook(drop_pending_updates=True)` on startup. Therefore **Telegram redelivery is not a dependable recovery plan for a queued/uncommitted turn in this runtime**. Before claiming crash-safe ordered admission, the intake must tie update confirmation to durable phase-1 completion (or persist a bounded, idempotent inbox before confirmation), avoid dropping pending updates on restart, and handle duplicate redelivery. The existing DB session/cutoff alone preserves the last committed boundary but cannot recreate an update lost before admission. These are proposed deployment changes, not implemented here.

On DB failure during phase 1, do not acknowledge or launch generation. Roll back the admission/reset transaction, retain the update for retry if the ingress delivery contract permits, or surface a bounded failure without remapping it to a later session. A crash after successful phase 1 but before generation leaves a persisted user turn without a response; that is a separate recovery task. Do not silently claim end-to-end delivery from DB admission alone.

The preferred ingress sequencing is **single-process/single-poller only**. The current DEV Compose topology has one bot service and `bot.py` starts one poller; it does not prevent future replicas or another poller. Process-local lanes/locks cannot order events across workers. Multiple pollers or webhook workers require one shared ordered ingress owner or a durable partitioned queue with a defined upstream sequence and acknowledgement protocol. Production scaling must not reuse the single-process proof unchanged.

## Failure behavior and offline test plan

If an update's ordering cannot be established, defer or retry it within a bounded, explicitly tracked ingress mechanism; do not silently insert it into whichever conversation is current. If the source cannot supply a trustworthy order and the bound expires, fail closed with a distinct, user-visible failure where delivery is possible, rather than claiming the valid turn was accepted. Do not invent new coaching copy here. Stale 101 after committed cutoff 102 remains an ordinary safe rejection. Incomparable/missing private-chat markers remain rejected. Diagnostics should contain only reason/category and non-identifying correlation; no raw IDs or content.

Deterministic offline tests for an implementation slice:

1. Feed 101/102/103 in Telegram order while forcing handler/task start in reverse; verify 101 captured as A, 102 establishes B, 103 is committed in B. Test both 103-task-first and 102-task-first scheduling.
2. After 102 commits, deliver delayed 101; assert rejection, no history/ledger/draft contamination, and no positive acknowledgement.
3. Feed 102 then 104 (/new) with reversed long-work scheduling; 104 is the only active boundary. A delayed 102 cannot rotate backward.
4. Voice 103 follows /new 102 in ingress order; delay transcription and prove the original marker binds it to B without blocking 102 or another user.
5. Interleave two users; one user's slow phase 2 does not delay the other's phase 1. Long generation from 101 does not block admission of 102 and 103.
6. Fail a phase-1 DB transaction; assert rollback, no acknowledgement/generation, and no confirmation of an uncommitted ingress event under the proposed acknowledgement protocol.
7. Crash/restart after phase-1 commit but before generation, and separately before phase-1 commit; assert documented replay/deduplication behavior without relying on an in-memory queue.
8. Exercise callback-to-AI and quiz completion around /new; verify stale UI state cannot authorize an A turn in B and admin/moderation controls retain their current behavior.
9. Include missing/gapped message IDs and unrelated outgoing bot messages; never infer that a missing integer is an undelivered /new. Tests must use explicit event barriers, not arbitrary sleeps.
10. Assert no positive acknowledgement until ordered commit, no added model calls, unchanged latest-20/ledger scoping, and existing stale assistant/draft protections.

## Architecture decision record

**Decision.** For the present single-poller DEV architecture, move private-chat coaching admission and /new rotation to a short ordered ingress phase before handler task fan-out. Keep the DB conversation ID and /new cutoff as durable authority. Launch generation and other long work only after that phase. Treat callback/FSM transitions explicitly; never infer them from a referenced message ID.

**Why.** At the current DB admission point, a not-yet-run /new is unknowable. Sequencing short phase 1 at ingress establishes 102 before 103 when the polling stream delivers that order, without serializing model work.

**Ordering guarantee.** The proof is conditional on one polling owner and the Bot API's observed `getUpdates` stream presenting the relevant /new before the later private message. Update IDs and same-chat message IDs provide checks; neither a current DB watermark nor an arbitrary grace period reveals an unseen update. Broader delivery/restart guarantees require a durable acknowledgement or inbox design.

**Critical section.** Validate marker/eligibility, apply the short FSM transition, atomically insert/capture a user turn or rotate/delete/store cutoff for /new, then release. Voice reserves identity before transcription. No network, model, evaluator, or Telegram send inside.

**Generation concurrency.** Phase 2 runs independently after successful admission; same-session completion ordering remains unresolved.

**Acknowledgement timing.** Only after ordered phase-1 success, before long generation if desired; none for rejected or uncommitted events.

**Restart implications.** Existing startup drops pending updates and default polling can confirm before task completion. Make confirmation follow durable phase-1 admission or add an idempotent durable inbox, and change pending-update startup handling before claiming crash safety. A committed turn may still need response recovery.

**Multi-process implications.** One process/poller only for the first slice. More workers require shared ordered ingress; Python locks and queues do not suffice.

**Alternatives rejected.** Full-handler FSM isolation serializes model calls without proving message-ID order. Handler-created queues and DB watermarks cannot see unseen 102. Grace delays are probabilistic. `handle_as_tasks=False` on unchanged handlers serializes the full conversation and violates the short-critical-section goal.

**Risks.** (1) Bot API does not explicitly state a complete mapping from private message-ID order to all delivered update types; verify the polling contract. (2) Current startup/offset handling can lose uncommitted work on crash. (3) Voice needs pre-transcription capture and conditional later insert. (4) Callback/quiz FSM transitions can overtake /new if excluded. (5) Ingress backpressure, one slow DB operation, or another poller can invalidate the single-process liveness/ordering assumptions. Send-after-/new and same-session response ordering remain independent production blockers.

**Rollback strategy.** Keep the existing DB cutoff/atomic admission unchanged. Disable the proposed ingress sequencer and return to the current documented DEV limitation if offline validation fails; do not remove the durable session fence or reinterpret stored rows.

**First implementation slice.** Offline prototype a single-poller ordered phase-1 intake for private text, voice marker capture, and /new, with explicit per-update barriers in tests. Schedule existing long work after commit. Prove 101/102/103 under reversed handler scheduling and no lock across generation. Audit callback/FSM admission and startup confirmation as separate gates before production use. Do not alter prompts, evaluator, benchmark scenarios, or model calls.
