# DEV conversation-state carry-forward

This experiment carries only explicit older user boundaries/corrections and source-linked explicit rejection of an assistant hypothesis, whether that rejection is inside or outside the latest 20 raw messages. It does not infer motives or goals, track active themes, or use an LLM summarizer.

## Conversation boundary

The SQLite active_chat_sessions row is the source of truth for each Telegram user. New chat_messages and pending_drafts carry its opaque conversation_id. The latest 20 raw messages and the older deterministic ledger source are both read by user_id plus captured conversation_id. The ledger still contains at most four source-linked items and is never stored separately.

On first chat use, a new active ID is created. `/new` is authorized only by the explicit durable `users.coaching_eligible` marker, checked after the private-chat boundary and before any rotation or FSM mutation. It changes conversation scope; it does not grant coaching admission. An ineligible/legacy user receives `/start` guidance without session, cutoff, history, or draft mutation; a stale ineligible `AI_CHAT` cache is cleared while an in-progress quiz is preserved. An eligibility lookup failure fails closed. For an eligible user, /new rotates the active ID (or creates the first active row if absent) and deletes the user's chat rows and pending drafts still marked PENDING in one DB write transaction. New user/assistant rows and pending drafts use conditional inserts that reject a captured ID after it becomes stale. Approval/edit of a pending draft checks the active session and conditionally persists the delivered assistant turn. The FSM shadow ID is only a cache for observer correlation; it cannot authorize a DB write.

The schema upgrade is additive and repeat-safe: nullable conversation_id columns, nullable cutoff_chat_id/cutoff_message_id columns on active_chat_sessions, and a composite chat-history index. Legacy NULL rows are never assigned to a new session or read into its history. /new deletes them. No running database migration is performed by writing this code; init_db upgrades the configured DB only when that runtime is next started.

## Durable returning-text admission

`users.coaching_eligible` is a user-level resume marker, default false. `init_db` adds the field to older schemas without promoting legacy rows. The normal completed quiz-to-chat callback is the sole writer; it also ensures an active session ID. It is independent of quiz context: the completed quiz path writes users.test_result and quiz_result_verified=1 after validating the final score; the latter defaults to zero for legacy rows.

A private text message arriving with absent, empty FSM reads this marker and the current active session together. On success, the handler restores only `AI_CHAT` and the shadow ID, then uses the existing atomic admission and downstream direct/moderated route for that same message. The eligibility read creates no chat row or conversation ID. `/new` retains eligibility and rotates the active ID/cutoff as before. The coaching path reads the verified stored enum for an eligible user on every turn, so it wins over a conflicting FSM value. Missing, invalid, or unverified result means no archetype context, never a fallback. /new retains the result. End-user voice and audio use the same restoration helper before Telegram file lookup, download, or transcription; the transcript then follows this same coaching admission and direct/moderated path. Ineligible or non-private media do no expensive file work. Admin voice keeps its separate control path. Interrupted quiz recovery and /start product semantics remain separate work.

## Private-chat admission boundary

End-user coaching is private-chat only. /new, coaching text/voice, /start, quiz callbacks, and the AI-chat entry callback ignore non-private chats without changing coaching FSM, history, or drafts. Admin/moderation control paths retain their existing behavior. Private inbound turns use their original Telegram chat ID and positive message ID; transcribed text never supplies a synthetic marker.

/new records its chat/message cutoff while rotating the DB conversation ID and deleting old rows/drafts in one SQLite write transaction. An atomic user admission transaction checks that a private inbound message is newer than that cutoff, inserts it, and returns the captured conversation ID. Stale, missing, or incomparable markers are rejected without generation or a draft. An older /new cannot replace a newer cutoff. The DB cutoff is the persistence correctness fence; the short per-user asyncio lock only coordinates local FSM and DB admission and is released before generation. The lock is process-local, disappears on restart, and does not establish deterministic processing order across multiple bot workers. Scaling beyond the current single polling process needs stronger ordered ingress coordination before production use.

## Explicit already-answered correction

A new source-linked ledger event records only an explicit user correction that she already answered/said this, when it immediately follows an identifiable assistant question. It carries the assistant question's message ID and short exact wording, the user's message ID, and only the explicit correction phrase. It does **not** store or infer the earlier answer, certify that a question was fully answered, compare semantic paraphrases, or ban future questions on the topic.

The same compact annotation is supplied while the correction remains inside the latest 20 raw messages and after it leaves that window; raw history is unchanged. The user's newest explicit wording takes priority, and a genuinely new concrete clarification remains possible. Unlinked, ambiguous, uncertain, refused, or merely irritated turns are omitted from this event; false negatives are preferred. This event shares the existing four-item cap with boundaries and rejected hypotheses. Empty-state generator inputs remain unchanged.

## Remaining limits

A response can still be **sent** after /new if the reset occurs between the send-time active-ID check and Telegram delivery. The later DB insert is rejected, so persistence and ledger contamination are prevented, but user-visible send ordering still needs a separate pre-production solution. The same gap applies to moderated approval/edit. A valid post-/new message can still be processed before the reset handler and be deleted with the old conversation; the cutoff prevents an older message from entering the new conversation, but cannot recover this overtaken newer turn. Replies to concurrent messages inside one active conversation can finish out of order.

The full-history ledger source query remains unbounded **within the current conversation**. Recent recognized rejections are also labeled in the runtime block; raw history is unchanged. A later explicit user correction with a shared content word can suppress a rejection, but a semantic reopening without those lexical signals may leave the historical event visible. The current user message still has priority. The existing deterministic event detector may omit ambiguous statements by design. No extra model call, prompt change, or evaluator dimension is introduced. This remains DEV-only, not production-ready.
