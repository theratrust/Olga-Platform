# Ordered admission at polling ingress — offline prototype

This module and its tests are an offline proof of ordering, not a runtime feature. `bot.py` does not import `services/ordered_admission_prototype.py`; no dispatcher, handler, schema, prompt, evaluator, or benchmark wiring is changed. The existing private-chat gate, DB conversation ID, /new cutoff, atomic admission, stale-write guards, local lock, and ledger remain in place. The prototype assumes one ordered polling ingress and does not establish production readiness.

## Exact installed aiogram ingress point

Read-only inspection of the running DEV bot container found aiogram **3.30.0** at `/usr/local/lib/python3.11/site-packages/aiogram/dispatcher/dispatcher.py`.

- `Dispatcher._listen_updates`, beginning at line 197, calls `bot(get_updates)` at line 220, then yields each intact `Update` from the returned list at lines 247–248. It sets the next offset after yielding the update.
- `Dispatcher._polling`, beginning at line 354, consumes that iterator at lines 391–397. At lines 398–406, default `handle_as_tasks=True` creates an independent `asyncio.Task` for `_process_update`. **The usable pre-fan-out seam is this polling loop between receiving an intact `Update` and creating its handler task.** It would require a custom polling ingress/adapter or version-aware dispatcher integration; aiogram does not expose a ready-made middleware hook there.
- `Dispatcher.feed_update` (line 141) and update outer middleware run inside `_process_update`), after fan-out. Handler-level and FSM middleware locks therefore cannot prove 102 is admitted before 103. `Dispatcher.__init__` installs `DisabledEventIsolation` because `bot.py` supplies none. Turning on full-handler `SimpleEventIsolation` would hold a per-FSM-key lock through long generation and still would not sort tasks by message ID.
- `bot.py` constructs one dispatcher with `MemoryStorage`, calls `init_db()`, `delete_webhook(drop_pending_updates=True)`, then `dp.start_polling(bot)` without ordering overrides. The DEV Compose file has one bot service. Read-only `docker compose ps`/`docker compose top bot` showed one running DEV bot container with one `python bot.py` process. This validates the inspected deployment topology, not an enforceable prohibition on a second poller using the same token. `requirements.txt` uses `aiogram>=3.0.0`, so line numbers and behavior must be rechecked after dependency changes.

## Prototype contract

The single ingress producer calls `offer(IngressMessage)` **synchronously in the order received from polling**, before uncoordinated handler tasks are created. The local `polling_sequence` is an ordinal assigned by that producer; it is not Telegram `update_id`. `offer` rejects a decreasing/repeated ordinal rather than sorting tasks. Telegram `message_id` gaps are allowed. Only the original private-chat marker `(chat_id, positive message_id)` is validated; text content is never an ordering key.

Each `offer` reserves a per-user predecessor task before yielding control. Its short admission task waits for the previous admission for that user, then calls one injected atomic DB-style port: `admit` for text/voice or `rotate` for /new. The result is an immutable `AdmissionResult` with status, captured conversation ID, marker, and rejection reason. The test adapter uses the real `database.admit_user_message` and `database.rotate_conversation` against a **disposable SQLite fixture** for text and /new. Voice uses a separate simulated marker-reservation port: today's DB cannot safely write a transcript before transcription or reserve a voice marker. This test proves ordering of that proposed port, **not** that voice is ready to wire into the current DB.

After successful admission/reset, a separate task awaits acknowledgement and then runs downstream work. The next same-user admission does **not** await acknowledgement, transcription, model generation, observer work, or Telegram delivery. Rejected/stale/DB-failed updates launch neither acknowledgement nor downstream work. A positive acknowledgement is therefore after the relevant DB commit and before that update's simulated generation. A later /new can still invalidate old downstream work; the separate send-after-/new issue is untouched.

The deterministic tests force downstream start/completion in reverse order using `asyncio.Event` barriers, while DB admission still captures 101 under A, rotates at 102, and captures 103 under B. The old A row is then deleted by the intentional /new reset; 101's captured identity remains A. Different users have separate admission chains. No correctness test uses an arbitrary sleep.

## Restart, delivery, and deferred integration

If the process dies **after** admission commits but before generation, the user row or /new boundary is durable; generation may never happen. The offline test cancels downstream work after commit and confirms the admitted row remains. If the process dies **before** admission commits, it may be redelivered or lost: Telegram `getUpdates` confirms updates when the next request uses a higher offset, aiogram advances its local offset while iterating, and current startup requests `drop_pending_updates=True`. This prototype has no durable inbox, deduplication key, or offset-commit protocol and makes no restart-delivery guarantee. [Telegram Bot API: getUpdates](https://core.telegram.org/bots/api#getupdates).

Callbacks and quiz events are deferred. They are not ordinary incoming Message events with their own comparable `message_id`; their referenced bot-message ID is not a safe /new ordering marker. Their short FSM eligibility/transitions would need coordination with the same ingress stream or binding to a captured conversation ID. Long callback rendering and Telegram calls must stay outside the admission phase. Admin/moderation control paths retain existing behavior.

Wiring later would require: (1) a single polling owner with a tested pre-task ingress seam; (2) splitting current handlers so phase 1 is not repeated after the captured result is handed downstream; (3) a safe voice marker-reservation and later conditional transcript insert; (4) callback/quiz FSM coordination; (5) backpressure, task cleanup, and explicit error handling; and (6) a deliberate update-confirmation/startup policy for crash recovery. A second poller or multiple workers would break the local per-user ordering proof without shared ordered ingress. Current send-after-/new and same-session completion-order races remain unresolved.
